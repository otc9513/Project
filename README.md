# أمبير (Ampere) — Generator Management OS

منصة SaaS لإدارة المولدات الأهلية في العراق. Next.js + TypeScript + PostgreSQL (Prisma) + Auth.js (Google OAuth فقط) + Tailwind (RTL).

## حالة المراحل

- [x] **المرحلة 1 — الأساس**: هيكلة المشروع، Prisma Schema الكامل (كل الجداول)،
      Auth.js مع Google، إنشاء تلقائي للمساحة (Tenant) عند أول دخول،
      طبقة عزل المستأجرين المركزية (`requireTenantContext`)، middleware حماية المسارات.
- [x] **المرحلة 2 — RBAC + Feature Flags**: أدوار OWNER/ADMIN/ACCOUNTANT/COLLECTOR/TECHNICIAN
      عبر `requireRole()`، ونظام `isFeatureEnabled()` حسب خطة المستأجر مع تجاوز فردي.
- [x] **نموذج معياري**: وحدة `generators` الكاملة (Schema → Repository → Service →
      Server Actions) — كل الوحدات القادمة (مشتركون، فوترة، تحصيل...) تُبنى بنفس النمط
      حرفيًا.
- [x] **المرحلة 3 — المشتركون + الاشتراكات**:
      - وحدة `subscribers` كاملة: بحث/فلترة/ترقيم صفحات، منع تكرار رقم الهاتف،
        صلاحيات OWNER/ADMIN/ACCOUNTANT للتعديل.

      - أول صفحات واجهة فعلية: تسجيل الدخول بجوجل، تخطيط `/app` مع تنقّل سفلي

- [x] **المرحلة 7 — PWA**:
      - **Web App Manifest** (`public/manifest.json`): اسم/أيقونات (مولَّدة برمجيًا

      - **قرار هندسي (استبدال اعتمادية)**: استُبدلت `next-pwa` (متوقفة الصيانة
        عمليًا، ومعروف عنها مشاكل توافق مع Next.js 15 App Router) بـ
        `@ducanh2912/next-pwa` (نفس الفكرة، نسخة مُصانة فعليًا بدعم رسمي
        لـ App Router). Service Worker مبني من مصدر مخصّص (`worker/index.js`،
        وضع InjectManifest) بدل التوليد التلقائي الكامل، لأن معالجات
        push/notificationclick تتطلّب منطقًا مخصّصًا.
      - **⚠️ نقطة تحقّق لم تُختبَر فعليًا**: إعداد `next.config.js` (خيار
        `workboxOptions.swSrc`) لم يُشغَّل عبر `next build` حقيقي في هذه
        الجلسة (بلا اتصال إنترنت لتثبيت الحزم). إن ظهر خطأ بناء متعلق بهذا
        الخيار تحديدًا، راجع توثيق الحزمة المثبَّتة فعليًا وعدِّل اسم الخيار.
      - **الاستراتيجية أوفلاين**: `NetworkFirst` لصفحات التنقّل (تُخزَّن آخر
        نسخة ناجحة تلقائيًا، فتفتح لاحقًا أوفلاين — يحقق حرفيًا متطلب
        "فتح قائمة المشتركين دون اتصال")، و`StaleWhileRevalidate` للأصول
        الثابتة، وصفحة `/offline` احتياطية عند فتح مسار لم يُزَر من قبل.
      - **طابور دفعات أوفلاين للمحصّلين** (`src/lib/offline/`): IndexedDB
        (عبر `idb`) بدل localStorage (متزامن، سعة محدودة، غير متاح داخل
        Service Worker). زر الدفع في `/app/collection` يحفظ محليًا تلقائيًا
        عند انعدام الاتصال (أو عند فشل شبكي فعلي أثناء الإرسال)، ولافتة
        عامة (`OfflineSyncBanner`, مُركَّبة في تخطيط `/app`) تُزامن القائمة
        تلقائيًا فور عودة الاتصال وتعرض نتيجة المزامنة (نجاح/تعارض).
      - **قرار هندسي مهم**: المزامنة تلقائية عند حدث `online` وعند فتح
        الصفحة — **وليس** عبر Service Worker Background Sync API — لأن
        Background Sync **غير مدعوم إطلاقًا على Safari/iPhone**، وهذا يمسّ
        فعليًا محصّلين ميدانيين قد يستخدمون آيفون. معالجة التعارض: أي دفعة
        يفشل تطبيقها عند المزامنة (فاتورة أُلغيت أو اكتمل دفعها من جهاز آخر
        بينما كان الجهاز غير متصل) **تبقى في الطابور مع رسالة الخطأ** بدل
        حذفها بصمت، ليحلّها المحصّل يدويًا ولا يضيع أثر أي مبلغ.
      - **Push Notifications**: نموذج `PushSubscription` جديد في Prisma
        (منفصل عمدًا عن `PushNotificationCampaign` الموجود مسبقًا للمرحلة 8،
        لأنه يمثّل الأجهزة المشترِكة فعليًا وليس "حملة" مُرسَلة). وحدة
        `push` كاملة بنمط schema/repository/service/actions، ومكتبة
        `web-push` (تتطلّب مفاتيح VAPID تُولَّد محليًا بالأمر
        `npx web-push generate-vapid-keys` ثم تُحفَظ في `.env` — لا يجوز
        توليد أسرار تشفير داخل الكود مطلقًا). أول استخدام فعلي فوري:
        تعيين عطل لفنّي (`faultService.assign`) يرسل له إشعار Push +
        إشعارًا داخل التطبيق (`Notification` model) معًا، بأسلوب "أفضل
        محاولة" لا يُفشل عملية التعيين نفسها عند تعذّر الإرسال.
      - **استثناء موثَّق لقاعدة عزل الوحدات**: `faultService` يستورد الآن
        `pushService` من وحدة أخرى (`features/push`) — وهو الاستثناء الوحيد
        حتى الآن للقاعدة الصارمة "لا استيراد بين الوحدات" المتّبعة منذ
        المرحلة 1. مبرَّر لأن الإشعارات معنى عرضي (Cross-Cutting Concern)
        بطبيعتها عبر كل الوحدات، تمامًا مثل `AuditLog`، وليست جزءًا من
        منطق أعمال وحدة الأعطال نفسها.
      - **تجربة التثبيت** (`InstallPrompt`): يتعامل مع Android/Chrome
        (`beforeinstallprompt`) وآيفون (تعليمات يدوية، لأن Safari لا يُطلق
        هذا الحدث إطلاقًا) بمسارين منفصلين.

        (مُشفَّر دومًا - **لا نص صريح مخزَّن أبدًا**، عبر
        `src/lib/security/mfa-crypto.ts`: AES-256-GCM حقيقي عبر
        `node:crypto` القياسية، وليس تطبيقًا يدويًا)، `mfaRecoveryCodesHashed`
        (SHA-256 - مقبول لأكواد عشوائية عالية الإنتروبيا، بخلاف كلمات
        مرور بشرية)، `mfaEnrolledAt`.
      - **`Session`**: حقل `mfaVerifiedAt` جديد - **مرتبط بالجلسة نفسها
        وليس علمًا دائمًا على المستخدم**: كل جلسة/تسجيل دخول جديد يتطلّب
        اجتياز 2FA من جديد، حتى لو فعَّلها المستخدم سابقًا على جهاز آخر.
      - `src/features/platform-mfa/` (ميزة جديدة كاملة): `mfa.service.ts`
        (تسجيل بخطوتين - توليد سر وعرض QR، ثم تأكيد بكود 6 أرقام قبل
        التفعيل الفعلي؛ تحدّي دخول يقبل كود TOTP عادي أو كود استرداد؛
        تعطيل يتطلّب كودًا صالحًا حاليًا - يمنع اختطاف جلسة مفتوحة من
        تعطيل الحماية)، `platform-mfa.repository.ts`، Server Actions.
      - **أهم تعديل معماري**: `requirePlatformAdmin()` (نقطة الحراسة
        الوحيدة لكل لوحة Super Admin - راجع PR سابقة) صار يتحقق أيضًا من
        `mfaVerifiedAt` على صف الجلسة الحالية عبر قراءة كوكي الجلسة
        مباشرة (`src/lib/security/session-cookie.ts` - **⚠️ اسم الكوكي
        الافتراضي `authjs.session-token` غير مؤكَّد، نفس نقطة عدم اليقين
        في `e2e/auth-helper.ts`**) ويُعيد التوجيه لـ `/mfa-verify` إن
        كانت 2FA مُفعَّلة والجلسة غير مُتحقَّق منها - **بلا أي تكلفة أداء
        إضافية على حسابات لم تُفعِّل 2FA أصلاً** (الفحص يتوقف فورًا عند
        `mfaEnabled=false`).
      - `src/app/mfa-verify/` (مسار top-level مستقل عمدًا، خارج تخطيط
        `/super-admin`): لو كانت هذه الصفحة تحت `/super-admin` كانت
        ستُعيد توجيه نفسها لا نهائيًا (نفس البوابة تحرسها). تدعم `skipMfaGate`
        كخيار جديد في `requirePlatformAdmin(allowedRoles?, options?)`
        مخصَّص حصرًا لهذه الصفحة.
      - `src/app/super-admin/settings/security/` (صفحة إدارة جديدة):
        تسجيل/تعطيل تفاعلي كامل + رمز QR + عرض أكواد الاسترداد **مرة
        واحدة فقط** (غير قابلة للاسترجاع لاحقًا لأنها مُخزَّنة كـ hash).
      - اختبار وحدة جديد لأهم منطق أمني هنا: `mfa-gate.test.ts` - يتحقق
        من كل مسارات `requirePlatformAdmin` الأربعة (2FA غير مُفعَّلة/
        مُفعَّلة+غير مُتحقَّقة/مُفعَّلة+مُتحقَّقة/`skipMfaGate`).
      - `.env.example`: `MFA_ENCRYPTION_KEY` (32 بايت base64، `openssl
        rand -base64 32`).
      - **يتطلّب قبل الاعتماد عليها إنتاجيًا**: `npm install` (`otpauth`/
        `qrcode` غير مُختبَرتين فعليًا)، **التحقق الفعلي من اسم كوكي

## ملاحظة ختامية (كل المراحل الاثنتي عشرة - PR-1 إلى PR-12)

كل التنفيذ أعلاه جرى في بيئة sandbox بلا اتصال إنترنت (`npm install`
يفشل بـ 403) - **لم يُشغَّل أي أمر `build`/`typecheck`/`test`/`lint`
فعليًا طوال الجلسة بأكملها**. كل سطر كود هنا مبني على قراءة دقيقة
للمشروع الفعلي (أسماء الحقول، الأنماط المعمارية، القيود الموجودة مسبقًا)
ومعرفة تقنية عامة بالمكتبات المُستخدَمة، وليس على تحقق تنفيذي حقيقي.

**قبل الاعتماد على أي من هذا إنتاجيًا** (بالترتيب الموصى به):
1. `npm install` فعليًا (يحل كل شكوك أسماء واجهات الحزم الجديدة دفعة واحدة)
2. `npm run typecheck` (يكشف أي خطأ نوع فاتني في القراءة اليدوية)
3. `npm run test` (اختبارات الوحدة - منطق صحيح نظريًا، غير مُشغَّل فعليًا)
4. `npm run build` (يكشف أي تعارض بناء، خصوصًا تكامل Sentry/withSentryConfig)
5. مراجعة يدوية لكل نقاط "⚠️" الموثَّقة أعلاه تحديدًا (اسم كوكي الجلسة
   لـ PR-7/PR-11، خط PDF عربي فعلي لـ PR-6، واجهات otpauth/arabic-reshaper/
   bidi-js/@upstash/ratelimit)
6. `prisma migrate dev` على قاعدة بيانات حقيقية (لا مجلد migrations
   موجود أصلاً في المشروع منذ البداية)

## القرارات الهندسية الرئيسية

| القرار | السبب |
|---|---|
| عزل المستأجرين عبر `tenantId` في كل جدول + `requireTenantContext()` إلزامي | أبسط وأكثر أمانًا من Row-Level Security على مستوى DB لمرحلة أولى، مع نفس الضمانات إذا التزمت كل الاستعلامات بالـ repository layer |
| Server Actions بدل REST API منفصل | Next.js App Router يجعلها أسرع تطويرًا وأكثر أمانًا (لا API عام مكشوف) دون التضحية بإمكانية إضافة REST لاحقًا لتطبيقات خارجية |
| `Decimal` وليس `Float` لكل الحقول المالية | تفادي أخطاء التقريب في العمليات المالية |
| Session بنمط `database` وليس JWT | يسمح بإبطال الجلسات فورًا (مهم أمنيًا لموظف تم فصله) |
| `requirePlatformAdmin()` مستقل تمامًا عن `requireTenantContext()` (المرحلة 8) | يمنع أي خلط مستقبلي بين "عضو مستأجر" و"عضو فريق تشغيل المنصة" عبر نقطة حراسة واحدة بالخطأ |
| `SaasInvoice`/`SaasPayment` منفصلان عن `Invoice`/`Payment` (المرحلة 8) | فوترة "مستأجر يدفع للمنصة" مختلفة جذريًا عن "مشترك يدفع لصاحب مولد" - خلطهما تسريب بيانات بين طبقتين |
| Feature Flags تبقى Json (`Plan.features`) وليست جداول علائقية (المرحلة 8) | القرار الأصلي منذ المرحلة 2 يعمل فعليًا في كل الوحدات؛ لا مبرر لهجرة بيانات وJOIN إضافي لتحقيق نفس السلوك |

## التشغيل محليًا

```bash
cp .env.example .env      # ثم املأ القيم (DATABASE_URL, Google OAuth, STORAGE_*...)
npx web-push generate-vapid-keys   # يولّد مفتاحي VAPID لصق النتيجة في .env (Push Notifications)
npm install
npm run db:migrate
# اضبط SEED_SUPER_ADMIN_EMAIL في .env ببريدك (Google) قبل أول seed لتحصل
# على وصول Super Admin - راجع التعليق كاملاً في prisma/seed.ts
npm run db:seed
npm run dev
```

## هيكل المجلدات

```
src/
  app/            # صفحات Next.js (App Router) - يشمل /app (تطبيق المستأجر) و/super-admin (لوحة المنصة)
  features/       # كل وحدة عمل (generators, subscribers, billing, platform-tenants...) بنمط:
                   #   schema/ → repository/ → service/ → actions/
  lib/
    auth/         # إعداد Auth.js + Google OAuth
    tenant/       # عزل المستأجرين + onboarding + دورة حياة الاشتراك
    platform/     # حراسة لوحة Super Admin (منفصلة عن tenant/)
    audit/        # سجل التدقيق المركزي (مستأجرين + منصة)
    features/     # Feature Flags حسب الخطة + سجل أسماء المفاتيح
    storage/      # رفع/معالجة الأصول البصرية (S3-compatible + sharp)
    security/     # محدِّد المعدَّل (Rate Limiting)
  types/          # أنواع مشتركة (يشمل توسيع next-auth)
  config/         # ثوابت الإعداد
prisma/
  schema.prisma   # المصدر الوحيد لبنية القاعدة (كل الوحدات، بما فيها Super Admin)
  seed.ts         # الخطط الافتراضية + بذرة أول Super Admin (SEED_SUPER_ADMIN_EMAIL)
```
